# Database Strategy — Leave Management System (LMS)

## Technology

| Database | Purpose | Version |
|----------|---------|---------|
| PostgreSQL | Primary application data store | 15+ |
| PostgreSQL (separate schema) | Hangfire job persistence (`hangfire` schema) | 15+ (same instance) |

Single PostgreSQL instance in Phase 1. Hangfire uses a dedicated schema (`hangfire`) within the same database to avoid table name collisions.

## Naming Conventions

| Element | Convention | Example |
|---------|-----------|---------|
| Table | Plural snake_case | `leave_requests`, `comp_off_credits` |
| Column | snake_case | `start_date`, `reporting_manager_id`, `created_at` |
| Primary key | `id` (UUID) | `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` |
| Foreign key | `{referenced_table_singular}_id` | `user_id`, `leave_type_id` |
| Index | `ix_{table}_{columns}` | `ix_leave_requests_user_id` |
| Unique constraint | `uq_{table}_{columns}` | `uq_departments_name` |
| Enum column | Use PostgreSQL native enum or varchar with CHECK constraint | `status VARCHAR(20) CHECK (status IN (...))` |
| Timestamp | `TIMESTAMPTZ` (UTC) | `created_at TIMESTAMPTZ DEFAULT NOW()` |

## Primary Key Strategy

- All tables use `UUID` primary keys generated by PostgreSQL (`gen_random_uuid()`)
- Never use sequential integer IDs (avoids enumeration attacks and simplifies eventual multi-node sharding)
- UUIDs stored as `UUID` type (not varchar)

## Migration Tooling

- **Tool**: EF Core Migrations (`dotnet ef migrations add` / `dotnet ef database update`)
- **Convention**: One migration per logical change; migration names are descriptive: `AddLeaveRequestsTable`, `AddCompOffExpiryDateIndex`
- **Apply on startup**: `app.MigrateDatabase()` extension called in `Program.cs` before accepting requests (ensures staging and prod are always up to date)
- **Never**: Hand-edit migration files after they are committed. If a mistake is made, add a corrective migration.
- **Seed data**: Separate idempotent seed method called after migrations; uses `ON CONFLICT DO NOTHING` / `FirstOrDefault` checks

## Soft Delete Strategy

- Application data is **never hard-deleted** (GDPR + audit compliance)
- Employees: `status VARCHAR(20)` column (`Active` / `Inactive`)
- Departments: `status VARCHAR(20)` column (`Active` / `Inactive`)
- Leave types: `is_active BOOLEAN` column
- Comp-off credits: `status VARCHAR(20)` column (`Active` / `Used` / `Expired`)
- EF Core global query filters: `modelBuilder.Entity<User>().HasQueryFilter(u => u.Status == "Active")` applied per entity where appropriate; use `IgnoreQueryFilters()` only in admin/audit contexts
- GDPR anonymization: `name = "Anonymized"`, `email = "anon-{id}@deleted.local"`, `phone = null`, `status = "Inactive"`

## Audit Trail

- Table: `audit_logs` — append-only, no UPDATE or DELETE ever issued
- All state-changing operations must call `AuditService.LogAsync(...)` before returning
- `old_value` and `new_value` stored as `JSONB`
- Retention: minimum 3 years (physical deletion requires a DB admin operation outside the application)
- Row-level security consideration: add PostgreSQL trigger to block `UPDATE`/`DELETE` on `audit_logs` in production

## Multi-Tenancy Model

None — single-organization deployment. No tenant_id columns required.

## ORM Guidance (EF Core)

- Use EF Core Code-First with Fluent API configuration (no Data Annotations on domain entities — keep domain clean)
- Entity configurations in `LMS.Infrastructure.Persistence.Configurations/[EntityName]Configuration.cs`
- Always specify table name explicitly: `builder.ToTable("leave_requests")`
- Always configure all foreign keys with explicit cascade rules: `DeleteBehavior.Restrict` (default) unless cascade is intentional
- Use `HasColumnName("snake_case_name")` for every property
- Decimal precision: use `builder.Property(x => x.Balance).HasPrecision(5, 1)` for leave balances (max 999.5 days)
- Enum columns: store as `string` (varchar), not integer, for readability in DB queries
- Never use EF Core lazy loading (causes N+1 queries); use explicit `.Include()` or projection

## Indexing Rules

All of the following must be indexed:
- Every foreign key column (`user_id`, `leave_type_id`, `department_id`, `reporting_manager_id`, etc.)
- `leave_requests.status` — frequent WHERE filter
- `leave_requests.start_date`, `leave_requests.end_date` — date range queries
- `leave_requests.user_id` + `status` — composite index for "my pending requests"
- `approval_steps.leave_request_id` + `level` — approval lookup
- `audit_logs.user_id`, `audit_logs.action`, `audit_logs.created_at` — audit search
- `notifications.user_id` + `read` — unread count polling
- `comp_off_credits.user_id` + `status` + `expiry_date` — expiry job query
- `holidays.date` — working-day check (hot path)
- `departments.name` (unique), `departments.code` (unique) — uniqueness checks

## Connection Management

- Connection string via `ConnectionStrings__DefaultConnection` environment variable
- Hangfire: `ConnectionStrings__HangfireConnection` (may point to same DB with different schema)
- EF Core connection pooling: default Npgsql pool (min 1, max 100)
- TLS required: `sslmode=require` in connection string for staging and production
- Local dev: `sslmode=disable` acceptable in Docker Compose
